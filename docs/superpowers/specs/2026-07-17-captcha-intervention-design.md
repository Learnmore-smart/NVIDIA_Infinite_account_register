# 验证码人工干预与自动继续设计

## 目标

让自动化在遇到 hCaptcha、reCAPTCHA 或其他安全挑战时，以中文明确提示人工操作；人工完成后自动继续，同时保留可靠的手动检查按钮。

## 已确认的产品要求

- 目标浏览器顶部红色横幅在等待验证码时显示“⚠️ 请人工干预”。
- 本地控制台网站使用简体中文；`Gmail`、`API Key`、`NVIDIA` 等专有名词保留英文。
- 默认自动检测验证码是否完成，并在确认完成后继续执行。
- 弹窗保留“我已完成，立即检查”按钮作为兜底。
- 点击按钮后必须显示真实检查进度和结果，不能立即恢复成原文字而让用户误以为无响应。

## 根因

当前 `detectCaptcha()` 把“验证码 iframe 仍存在”等同于“挑战仍未完成”。hCaptcha 完成后 iframe 通常仍留在 DOM 中，因此按钮虽然成功调用 `/api/captcha-solved` 并唤醒 runner，runner 两秒后仍匹配同一个 iframe，又进入等待状态。前端按钮则在 HTTP 请求结束时立即恢复原文，没有等待 runner 的检查结果，所以表现为点击无反应。

## 状态与数据流

1. Runner 检测到未完成挑战，将状态设为 `waiting`，目标页横幅改成“请人工干预”。
2. Runner 每秒自动检查一次。检查顺序为：
   - 先读取标准验证码响应字段，例如 `h-captcha-response`、`g-recaptcha-response` 和 Turnstile 响应；存在非空 token 即视为完成。
   - 若没有 token，再检查原挑战选择器是否已消失或不可见。
3. 用户也可以点击“我已完成，立即检查”。服务器把状态切到 `checking` 并唤醒同一个等待流程。
4. 若验证完成，runner 广播 `resolved`，隐藏弹窗、恢复运行状态和普通自动化横幅，然后继续原流程。
5. 若仍未完成，runner 再次广播 `waiting` 并附带“仍未检测到验证结果”，按钮恢复可用。
6. 停止任务时必须解除等待并停止轮询，不留下定时器或悬挂 Promise。

## 界面设计

- 浏览器目标页横幅：等待时为红底白字“⚠️ 请人工干预”。
- 控制台弹窗标题：“请人工干预”。
- 正文说明当前用户、检测到的挑战类型，以及“完成验证后系统会自动继续”。
- 状态提示：“正在自动检测验证结果…”；手动点击后显示“正在检查…”。
- 兜底按钮：“我已完成，立即检查”。
- Dashboard 的静态文本、状态标签、按钮、表单、空状态、提示与错误信息全部翻译为中文，保留已确认的专有名词。

## 实现边界

- `runner.js`：验证码完成判定、条件轮询、手动唤醒、横幅状态。
- `server.js`：权威验证码状态与 `waiting/checking/resolved` SSE 广播。
- `public/index.html`：中文静态界面与干预弹窗文案。
- `public/index.js`：中文动态文案、按钮状态、SSE 驱动的检查反馈。
- `public/index.css`：仅补充必要的状态提示样式，不重新设计整体布局。

## 错误处理

- 手动检查请求失败时，按钮恢复可用并显示中文错误。
- Runner 页面关闭或 CDP 检查失败时记录警告，并保持可停止，不把异常误判为验证成功。
- 重复点击或没有待处理挑战时，服务器返回明确的中文错误，不重复解除 Promise。

## 测试策略

- Runner 单元测试：iframe 留存但响应 token 已填写时应自动判定完成。
- Runner 单元测试：token 为空且挑战仍可见时继续等待。
- Runner 单元测试：自动轮询完成后无需按钮即可继续。
- Runner 单元测试：手动唤醒后触发立即检查，停止时解除等待。
- Server/状态测试：`waiting -> checking -> resolved` 状态和无活动挑战错误。
- 前端测试：中文文案、按钮 pending 状态以及 SSE 后恢复/隐藏行为。
- 最终运行完整测试和 JavaScript 语法检查；不干扰当前正在运行的浏览器实例。
